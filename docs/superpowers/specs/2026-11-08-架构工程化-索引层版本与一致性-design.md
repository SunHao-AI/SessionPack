## 1. 背景与定位裁定

catalog 索引库从 Spec 1 起就没有版本概念：`PRAGMA user_version` 恒为 0，
`init_schema` 全部 `CREATE ... IF NOT EXISTS`，对"表已存在但形状不对"的库
不做任何检查。FTS 与 messages 的成对写入靠 `upsert_message` 的调用约定维持
（无触发器），一旦漂移，3 字以上检索**静默漏结果、无异常**，doctor 只报计数
不判定。本轮立项时经用户选定为主题 A。

撰写前已用实跑探针把现状钉死（探针脚本在仓库外 `Temp\spike7\`，
逐字输出见 §2–§4 各小节，另有一次性能实测定量，见 §3"为什么不逐行对账"）。
两条定位问题决定方案形态，本轮裁定如下：

- **索引库是纯派生缓存，允许整库重建**：归档 zip 独立于索引库存在，
  `import` 有逐文件增量续传状态。所以一致性问题的"解药"永远是重建，
  不需要为任何索引形状设计原地迁移——版本门禁的职责是**及时、明确地失败**
  并把用户导向重建，而不是修库。
- **门禁落点唯一**：`init_schema` 是全部三条生产写路径
  （`cli/write_cmds.py:31` import、`:191` run_pull、`importer/run.py:44`
  import_source）的公共前置，改这一处即全覆盖，读路径单独补"未来版本"提示。

处理总览：

| 项 | 实测定性 | 处置 |
|----|---------|------|
| VER-1 | 零版本逻辑；史前形状老库静默通过，报错滞后且指向错误位置（探针 A/B） | **纳入 P1**：`user_version` 打 1 戳 + 未来版本 fail-closed + 老库缺列即刻报错导向重建 |
| FTS-1 | 漂移后 3 字词检索静默 0 条；doctor 报计数不判定（探针 C/D） | **纳入 P1**：doctor 行级对账（计数法，零成本）+ 警告 + 文本渲染 |
| FTS-2 | 漂移无安全修复路径（无任何重建命令） | **纳入 P1**：`rebuild --fts`（同事务全量重建 + 集合级自检） |
| FTS-3 | 库形状坏到 `init_schema` 拒绝时，用户无路可走 | **纳入 P2**：`rebuild --from-archives`（归档全量重建，临时库 staging + 换入 + 备份） |
| — | 逐行（内容级）对账 | **不做**：实测 5 万行超时（§3），且修复手段本就是整表重建 |
| — | FTS 触发器双保险 | **不做**：见 §7 |

## 2. VER-1：`user_version` 版本门禁（P1）

### 现状复现（探针 A/B，逐字）

```
=== 探针 A：init_schema 后 user_version ===
tokenizer: trigram
user_version: 0

=== 探针 B：史前形状老库（sessions 无 content_hash）===
老库 sessions 列: ['session_id', 'project_id', 'source_kind', 'title',
'created_at', 'updated_at', 'status']
refresh_session_hashes -> OperationalError no such column: content_hash
```

（完整输出中老库列为
`['session_id', 'project_id', 'source_kind', 'title', 'summary',
'created_at', 'updated_at', 'status']`，即"少了 `content_hash` 的 sessions"。）

两个事实：

1. `init_schema` 后 `user_version` 仍是 0——全仓无任何版本读写，
   未来 schema 演化（加列、改 FTS 分词器）没有任何检测点。
2. 对"表齐全但缺列"的史前库，`CREATE TABLE IF NOT EXISTS` 全部静默跳过，
   `init_schema` **原样通过**；错误滞后到下一次
   `refresh_session_hashes` 的 UPDATE 才抛 `OperationalError`，
   报错指向写入路径而不是病根，用户无从知道该重建。

### 方案

版本模型：`SCHEMA_VERSION = 1`（当前形状即 v1）。

1. `conn.py` 新增异常 `CatalogVersionError(RuntimeError)`
   （对齐 `ConfigWriteError` / `ArchiveError` 的 `RuntimeError` 子类惯例）
   与 `CatalogSchemaError(RuntimeError)`。
2. `init_schema` 在现有 DDL 之后、`commit` 之前加门禁：
   - 读 `PRAGMA user_version`：
     - `== 0`（本工具建的史前库，从未打过版本）→ 校验 v1 必需列
       （见第 4 条）→ 通过则 `PRAGMA user_version = 1`；
     - `0 < v < SCHEMA_VERSION` → 抛 `CatalogVersionError`，文案含版本号与
       "运行 sessionpack rebuild --from-archives 重建"；本轮无迁移路径
       （§7），未来 v2 落地时再补前向迁移；
     - `v == SCHEMA_VERSION` → 直接通过；
     - `v > SCHEMA_VERSION`（工具比库旧）→ 抛 `CatalogVersionError`，
       文案含"请升级 sessionpack 后重试"。
   - **全新库**（`init_schema` 前无任何表）同样落 `user_version = 1`。
3. `tokenizer_of` 旁边新增只读 `schema_version(conn) -> int`，
   供 doctor 与 CLI 显示；对不存在的库不做判断（读路径仍由
   `require_catalog` 把关）。
4. 必需列校验 `_required_columns`：对 `sessions`/`messages`/`projects`
   三张核心表用 `PRAGMA table_info` 比对 v1 列名清单（逐字取
   `SCHEMA` 现形状：sessions 9 列、messages 10 列、projects 5 列）。
   缺列即抛 `CatalogSchemaError`，文案逐字含**缺失列名**与
   "运行 sessionpack rebuild --from-archives 重建索引"。
   探针 B 的报错从"滞后到 UPDATE、指向错误位置"变为
   "`init_schema` 当场拒绝、指向病根"。
5. 读路径不动（`connect_readonly` 不建库不写版本），仅在
   `diagnostics._catalog_section` 用 `schema_version` 补显示（§3）。
6. CLI 接线：`cmd_import` / `run_pull` 捕获两个新异常，转
   `EXIT_ERROR` + 文案（`run_pull` 现状已有 `except sqlite3.Error`
   兜底在 `cli/write_cmds.py:243` 之前，新异常在其前捕获）；
   不改 `cli.main` 的兜底。

### 为什么不选"缺列自动 ALTER 补齐"

索引库是纯派生缓存（§1 裁定），重建路径（§5）保证存在且比迁移便宜：
ALTER 补齐只救"缺列"一种形状，救不了缺表、FTS 分词器不符、未来任意形状
漂移，反而制造"半新半旧"的中间态库。fail-closed + 导向重建是唯一
不需要为每种形状写代码的防线。

### 验收

- 新增测试 ≥6：新库打 1 且幂等 / 未来版本库（预置 `user_version=99`）
  拒绝且文案含版本号 / v1 库重复 `init_schema` 零副作用 /
  探针 B 形态老库即刻抛 `CatalogSchemaError` 且文案含 `content_hash` /
  CLI import 遇未来版本库返回 `EXIT_ERROR` 不崩栈 /
  `schema_version` 对未打戳库返回 0。
- `test_catalog.py` / `test_importer.py` 既有 60+ 测试零改动通过
  （打戳对正常路径不可见）。

## 3. FTS-1：doctor 行级对账（P1）

### 现状复现（探针 C/D，逐字）

```
=== 探针 C：FTS 漂移 → 检索静默漏，无异常无警告 ===
正常 search('冲锋衣'): 1 条
漂移后 search('冲锋衣'): 0 条 ← 3 字词走 FTS，静默漏 0 条
stats: {'projects': 0, 'sessions': 1, 'messages': 1, 'fts_rows': 0}

=== 探针 D：doctor 对同一漂移库只报计数，不判定 ===
catalog 段: {'path': '...\catalog.sqlite', 'exists': True, 'ready': True,
'stats': {'projects': 0, 'sessions': 1, 'messages': 1, 'fts_rows': 0},
'tokenizer': 'trigram', 'size_bytes': 73728, 'archives_bytes': 0}
warnings: []
```

`search_messages` 的三层降级（≥3 字走 FTS、<3 字走 LIKE、FTS 异常也降级）
决定了漂移的表现：**2 字词一切正常，3 字词静默 0 条**——用户会以为
"没搜到"而不是"索引坏了"。doctor 把 `fts_rows: 0` 摆在你面前但不判定。

### 为什么不逐行对账（性能实跑，逐字）

5 万行 messages + 50% FTS 漂移的库上实测三种对账实现：

| 实现 | 耗时 | 结论 |
|---|---|---|
| 两条 `COUNT(*)` 差值 | **0.02 ms** | 采用（doctor 常开） |
| 读两侧 `(session_id, message_id)` 做 Python set 差集 | 0.745 s | 采用（仅 `rebuild --fts` 自检，一次性成本） |
| `NOT EXISTS` 逐行 SQL 对账 | **>2 分钟超时未跑完**（手动中止） | 排除 |

根因：`message_fts` 的 `session_id`/`message_id` 是 `UNINDEXED`
（只存不索引），逐行探查是 O(N×M)。`message_fts` 是 contentless DDL
（未用 `content=` 外部内容表），逐行比对正文还要先全表取出，更不可行。

### 方案

行级对账分两档，**都是行存在性判据，不比对正文**（边界见 §7）：

1. `catalog/read.py` 新增只读 `reconcile_fts(conn) -> dict`：

   ```python
   {"messages": n, "fts_rows": n, "fts_missing": n, "fts_extra": n,
    "drift": bool}
   ```

   - `message_fts` 不存在（`tokenizer_of == "none"`）→ 全 0 +
     `drift: False`（未建索引不算漂移，与现状语义一致）；
   - 两侧计数相等 → 快速路径：`missing = extra = 0`，`drift = False`
     （两侧都从 messages 单调追加，计数相等时行级错位概率可忽略；
     这是 doctor 的常开判据）；
   - 计数不等 → 付 0.745s/5万行 的 set 差集成本拆出 `fts_missing` /
     `fts_extra` 精确值。
2. `diagnostics._catalog_section` 增加 `fts` 字段（= 上述 dict，
   未就绪时为 `None`）与 `version` 字段（`schema_version`）；
   **`stats` 四字段原样不动**（`test_server.py:95` 锁定）；
   `ready` 的判定逻辑不动（不新增退出码路径）。
   漂移时向 `result["warnings"]` 追加一条：
   `FTS 索引与消息表不一致：缺 {fts_missing} 条 / 多 {fts_extra} 条`
   `（共 {messages} 条消息），3 字以上检索可能静默漏结果，`
   `建议运行 sessionpack rebuild --fts`。
   库版本过新时 `ready: False` 并向 warnings 追加升级提示。
3. `run_doctor` 文本模式在"索引统计"行后追加：一致时
   `索引对账：一致（FTS {n}）`；漂移时逐行输出上述警告
   （复用既有 `同步警告：` 的渲染惯例，前缀 `索引警告：`）。
   退出码仍只由 `memory_root_exists` 决定——警告改变的是可见性，
   不是脚本契约。

### 验收

- 新增测试 ≥4：漂移库（`DELETE FROM message_fts` 后）doctor JSON
  `catalog.fts.drift is True` 且 `warnings` 含"rebuild" / 一致库
  `drift is False` 且零新增警告 / `message_fts` 缺失时 `drift is False` /
  文本 doctor 含"索引对账"行与"索引警告"行。
- `test_server.py` 与 doctor JSON 既有断言零改动通过（只增字段）。

## 4. FTS-2：`rebuild --fts` 安全重建（P1）

### 现状

全仓无任何重建命令（`parser.py` 子命令仅 doctor/scan/import/serve/
export/verify/push/pull）。FTS 漂移后唯一手工解法是用户自己对库执行
`DELETE FROM message_fts` + 逐行补写——没有任何工具面。

### 方案

1. `catalog/write.py` 新增 `rebuild_fts(conn) -> int`：
   **单事务**内 `DELETE FROM message_fts` →
   `INSERT INTO message_fts(session_id, message_id, text)`
   `SELECT session_id, message_id, body FROM messages ORDER BY rowid`，
   返回重建行数后 commit。
   - 全删重插顺带治好计数/集合都查不出的**正文级**漂移（§7 的检出边界）；
   - 同事务保证中途失败回滚到删除前，库不会停在半空；
   - 写语句全部落 `write.py`，E_SQL 白名单不扩大（lint_imports 注释中
     的"write.py 15 处"计数同步更新）。
2. 重建后自检：用 `reconcile_fts` 的 set 差集做集合级验证
   （`missing == extra == 0` 才算成功），残留漂移按行级计数如实报告。
3. CLI 新增 `rebuild` 子命令（`parser.py` + `write_cmds.run_rebuild/cmd_rebuild`）：
   - `--fts` 为本轮唯一实装模式且为缺省：库不存在 → `EXIT_USAGE`
     "索引不存在，请先运行 sessionpack import"；
     输出 `FTS 重建完成：{n} 条`，`--json` 给
     `{"rebuilt": n, "fts": {...对账结果...}}`；
   - `--from-archives` 见 §5；两 flag 互斥。
4. 并发说明（写入 spec 不留白）：`rebuild --fts` 单事务覆盖整个重建，
   与另一进程的 `upsert_message` 并发时由 SQLite 锁串行化，
   后提交者胜出，不产生半态；doctor 事后可检出。

### 验收

- 新增测试 ≥4：漂移库 `--fts` 后 `search_messages('冲锋衣')` 恢复命中 /
  重建后 `reconcile_fts` 全一致 / 幂等（连跑两次行数不变）/
  库不存在时 `EXIT_USAGE`。
- `--json` 结构如上；文本含"FTS 重建完成"。

## 5. FTS-3：`rebuild --from-archives` 全量重建（P2）

### 定位

服务两种场景：§2 门禁拒绝的坏形状库；用户主动想从归档清重建。
数据源是 `layout.archives` 下的 zip（独立于索引库，`verify_archive`
可独立校验）。**会丢弃仅存在于内存树、从未导出进任何归档的会话**，
所以要求显式 `--yes` 确认。

### 方案

1. 新增 `sessionpack/rebuild.py`（L3，与 diagnostics/sync 同层，
   依赖 catalog=2 / importer=3 / archive=3 均合法）：
   `rebuild_from_archives(layout, *, assume_yes: bool) -> RebuildReport`。
   流程：
   - 枚举 `layout.archives/*.zip`（按文件名序）；为空 → 返回失败报告，
     文案"无归档包，无法全量重建，请运行 sessionpack import --memory-root …"；
   - 逐个 `verify_archive`，**任一 BAD 即中止**（fail-closed，
     原库分毫未动），文案含 zip 名与 issue code；
   - staging：复制 `catalog.sqlite → catalog.sqlite.staging`
     （WAL/SHM 不拷，原库此处只读打开校验后关闭）；
   - 对 staging 依次 `import_source(adapter, zip, staging, fresh=True)`
     （§5.2）；任一 zip 失败 → 删除 staging 中止，**原库未动**；
   - 全部成功 → `os.replace` 换入：原库改名为 `catalog.sqlite.bak`
     （覆盖旧 .bak），staging 改名顶上，清理 staging 的 WAL/SHM；
   - 报告含：归档数、各包导入行数、备份路径。
2. `import_source` 增加关键字参数 `fresh: bool = False`：为 True 时在
   `init_schema` 之后、开跑之前清空 `message_fts`/`messages`/`sessions`
   （三表 DELETE，落 `catalog/write.py`，新函数
   `clear_derived_rows(conn)`），`projects`/`import_*` 保留。
   默认 False 行为与现状逐字节一致。
3. 安全不变量（写入测试）：**失败路径原库字节级不变**（换入前原库只读）；
   换入成功后必存在 `.bak`；`--from-archives` 缺 `--yes` 直接
   `EXIT_USAGE` 并说明后果。

### 验收

- 新增测试 ≥4：正常全量重建后 `stats` 与源一致且 `.bak` 存在 /
  含 BAD zip 时中止且原库字节不变、无 staging 残留 /
  缺 `--yes` 拒绝 / 无归档时给出 import 指引。
- CLI 文本逐包一行 + 汇总行；`--json` 给 `RebuildReport.as_dict()`。

## 7. 范围外

- **schema 前向迁移**：`0 < user_version < SCHEMA_VERSION` 一律拒绝并导向
  重建；未来 v2 落地时再写迁移，本轮只留门禁位。
- **FTS 正文级漂移的"检出"**：判据是行存在性（计数/集合），不比对正文。
  修复手段（全删重插）顺带覆盖正文漂移，但 doctor 检不出
  "行数一致但正文被改"的构造形态——不为它付全表正文扫描的常驻成本。
- **FTS 触发器**：`AFTER INSERT ON messages` 触发器可以杜绝应用层双写
  漂移，但会改掉 `upsert_message` 被 `test_import_contracts` 契约锁定的
  双写语义，且挡住未来改用 `content=` 外部内容表的演化。检测+修复
  已闭环，暂不引入。
- **doctor 退出码语义**：漂移不改变退出码（理由见 §3 方案第 3 条）。
- **`pull` 的对账**：pull 后不自动跑对账（性能与职责考虑），doctor 随时可查。
- 零依赖、不写 CI、`spike/` 不动、BASELINE 与 E_SQL 白名单均不动。
