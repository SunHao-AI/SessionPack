当轮主题的裁剪，本主题从未独立评审过。本文档做这次评审。

## 2. CFG-1：`set_sync_dir` 写回加保真校验（P1）

### 现状复现（探针 A：`_dump_toml` 有损，逐字）

`_dump_toml` 只认「顶层标量 + 一层扁平段」，段值统一走
`_toml_value`，末尾 `json.dumps(str(value))` 兜底：

| 手写输入 | 写回输出 | 往返等价 |
|---|---|---|
| `[sync]\ndir="D"\n[sync.auth]\ntoken="t"` | `auth = "{'token': 'tk'}"` | ✗ |
| `[meta]\nlast_run = 2026-01-01` | `last_run = "2026-01-01"` | ✗ |
| `[[repos]]\nname="x"` | `repos = ["{'name': 'x'}"]` | ✗ |
| `["my key"]\nx = 1` | `[my key]` | ✗ **文件不再可解析** |
| `# 注释` | 注释消失 | —（可接受） |

真实端到端（探针 A'）：用户文件含 `[meta]` 日期 + `[sync.auth]` 嵌套，
跑一次 `push --dir` 后 `sync.auth` 变成字符串 `"{'token': 'tk'}"`，
`meta.last_run` 变成字符串，注释全丢。

### 现状复现（探针 B：语法损坏文件上的整段丢弃）

`load_config` 对语法损坏返回 `({}, [警告])`——"按空配置处理"。
`set_sync_dir` 拿这个空 dict 当既有内容，于是：

```
输入: [other]\nkeep = "please"\n[sync]\ndir = "D   #缺右引号
set_sync_dir 后: [sync]\ndir = "D:\\New"        ← [other] 整段消失
```

文件本来只是有一处笔误，用户跑一条 `push --dir` 后其他段被永久删除。
这是 Spec 5 之前清单 C1「定时炸弹」的同类残留：C1 修的是"丢未知段"，
只覆盖了可解析且扁平的情况，**没有覆盖"解析失败即视为空"这条路径**。

### 方案

写盘前先判定"既有内容能否被 `_dump_toml` 保真往返"，不能就拒写
（fail-closed，无副作用——校验在 `os.replace` 之前）：

1. `config.py` 新增异常 `ConfigWriteError(RuntimeError)`
   （对齐 `audit.ReadBoundaryError` / `archive.verify.ArchiveError`
   既有的 `RuntimeError` 子类惯例）。
2. 新增纯函数 `_unfaithful(data) -> list[str]`，返回不可保真的原因
   （空列表 = 可安全写回）。**判定对象是"段内的值"，不是"段的值"**——
   段落本身在 `data` 里永远是 dict（`sync` 与 `other` 都是），
   把"值是 dict"当成不可保真会让每次正常写回都被拒、并直接打破
   `test_set_sync_dir_preserves_other_sections`。规则：

   | 检查 | 判据 | 对应探针形态 |
   |---|---|---|
   | **裸键名**（段名 + 段内键名 + 顶层键名，三者同一条判据） | 不匹配 `^[A-Za-z0-9_-]+$` → 报告该名 | `["my key"]` / `[other]` 内 `"my key" = 1` / 顶层 `"my key" = 1`——**三种形态实测写回后均为 `TOMLDecodeError`，文件不可解析** |
   | 段内值 | 是 `dict` → 报告 `段名.键名`（嵌套段） | `[sync.auth]` → `auth = "{'token': 'tk'}"` |
   | 段内值 | 是 `date`/`datetime`/`time` → 报告 | `last_run = 2026-01-01` 退化成字符串 |
   | 段内值 | 是 list 但元素不全属 `bool/int/float/str` → 报告 | `[[repos]]` 表数组读回成 `[dict]` |
   | 顶层值 | 是 dict → 按"段"走上二/三/四条；是标量 → 按"值"走上三/四条 | `verbose = true` 可保真（探针实测往返等价） |
   | **放行面** | `bool/int/float/str` 与纯标量 list；**空段**（`[empty]` 实测可保真） | `test_set_sync_dir_preserves_other_sections` 的 `name/count/flag` 必须继续放行 |

   裸键名判据覆盖键名而非仅段名，是实施前补跑探针的结论：`_dump_toml`
   对段名与键名一视同仁地不加引号，只校验段名会漏掉
   `[other]\n"my key" = 1` 这种同样把文件写坏的真实形态。

   `sync` 段自身不做段名/段内特殊豁免：它由 `set_sync_dir` 写入的
   `dir` 恒为 str，天然落在放行面上。

   **`sync` 段原本是标量时（`sync = "D"`）按"修复"处理，不拒写**：
   `set_sync_dir` 现状就用 `dict(section) if isinstance(section, dict) else {}`
   把它替换成正常的 `[sync]` 表，合并后落在校验放行面上。这是期望行为——
   用户正是想用这条命令把配置写对，§3 的形状警告已在同一轮提示过他；
   拒写只会让他无路可走。既有
   `test_corrupt_config_treated_as_empty_with_warning` 只覆盖语法损坏，
   不覆盖此形态，故新增一条测试锁定"标量 sync 被正常修复且往返保真"。
3. `load_config` 拆成两层，让"致命"与"形状"两类警告可分：
   `_read_toml(root) -> (dict, list[str])` 只做读 + 解析，警告**只含**
   现状那一条（`(tomllib.TOMLDecodeError, OSError)` → "config.toml 解析失败，
   已按空配置处理"，`config.py:19-20`）；
   顶层非 dict 分支（`config.py:21`）保持现状**不产生警告**——`tomllib.load`
   按规范必然返回 dict，那是防御性死代码，本轮不借机加警告
   （加了也无法用真实文件测，属无验证面的改动）。
   公开 `load_config` = `_read_toml` + §3 的 `_shape_warnings`，
   返回签名与既有测试断言的警告行为完全不变。
   `set_sync_dir` 改调 `_read_toml`，顺序为：**致命警告非空即抛**
   （堵探针 B）→ `_unfaithful(合并后 data)` 非空即抛（堵探针 A）
   → 才写临时文件 + `os.replace`。
   注意校验对象是**合并 `[sync].dir` 之后**的完整 data，否则
   原本可保真的文件会因为新写的 `sync` 段而漏判。

   **为何不能直接"警告非空即拒写"**：§3 的形状警告（如 `[snyc]` 拼错）
   也走 `load_config` 通道，而形状问题的**解药恰恰是跑一次
   `push --dir`**（它会补出正确的 `[sync]` 段，并原样保留 `[snyc]`，
   后者由 `test_set_sync_dir_preserves_other_sections` 锁定的行为正是
   所需）。若写路径对形状警告也 fail-closed，§3 给用户的指引就成了死路。
   因此写侧只认致命警告，形状警告只影响读侧提示。
4. 文案含具体定位（段名/键名）与出路，例如：
   `config.toml 含无法保真保留的内容：[sync.auth]（嵌套段）、[meta].last_run（日期）；`
   `已拒绝写入以免损坏你的文件，请手工维护 [sync] 段的 dir 键`。
5. CLI 接线：`run_push` 用 `try/except ConfigWriteError` 包住
   `set_sync_dir`，转成 `CommandResult(EXIT_ERROR, out_lines=lines, err_lines=[...])`
   ——**推送已成功这一事实仍要报告**，只有"落配置"这一步失败。
   不改 `cli.main` 的兜底 `except Exception`（不改既有行为）。

### 为什么不选"写完整无损 writer"

用户已裁定 `config.toml` 是工具内部状态文件。零依赖手写完整 TOML writer
（bare/basic/literal 三态键、嵌套 inline table vs 独立段的首次出现顺序、
多行字符串、非 BMP 转义）是数百行且引入新的正确性面，服务的是一个
明确不该由用户手写的文件。护栏方案约 25 行，且把"静默损坏"变成
"明确拒绝 + 可操作提示"，风险面小一个数量级。

### 验收

- 新增测试 ≥7：嵌套段拒写 / 日期拒写 / 裸键名（段名与段内键名各一形态）
  拒写 / 语法损坏时拒写且**原文件字节不变** /
  拒写时不残留 `.tmp` / 纯扁平段继续可写（守 C1 行为）/
  标量 `sync` 被正常修复且往返保真。
- CLI 面 ≥2：`push --dir` 在拒写配置下仍返回已推送计数 + EXIT_ERROR +
  文案含 `[sync]`；`--dry-run` 不触发写路径（现状已不触发，加断言锁定）。
- `tests/test_config.py` 既有 7 个测试零改动通过。

## 3. CFG-2：配置形状诊断，消除静默失效（P2）

### 现状复现（探针 C，逐字）

| 手写内容 | `sync_dir()` | `load_config` 警告 | doctor |
|---|---|---|---|
| `[snyc]\ndir = "D"` | `None` | `[]` | 无提示 |
| `[sync]\ndir = 123` | `None` | `[]` | 无提示 |
| `sync = "D"` | `None` | `[]` | 无提示 |
| `[sync]\ndir = "D   #坏` | `None` | 1 条（仅语法） | 文本模式看不到 |

前三行是真实故障：**用户确实写了配置，但 push/pull 报
"未指定同步目录：请加 --dir DIR，或先运行 sessionpack push --dir DIR 落配置"**
（`cli/write_cmds.py:144` 与 `:180`），
把用户推向"再跑一次 push --dir"，而真正的问题是段名少了一个字母。
`[snyc]` 尤其危险：`set_sync_dir` 随后会把 `[snyc]` 原样保留写回
（`test_set_sync_dir_preserves_other_sections` 正是这个行为），
用户的错误配置永远躺在文件里且永远不生效。

### 方案

警告仍走既有 `load_config -> (data, warnings)` 通道，**不改任何签名**。
`load_config` 解析成功且 `isinstance(data, dict)` 后追加形状诊断
（新纯函数 `_shape_warnings(data) -> list[str]`）：

- `[sync]` 缺失但存在近似段名 → `difflib.get_close_matches("sync", keys)`
  命中则报 `config.toml 段落 [snyc] 疑为 [sync] 拼写错误，同步目录未生效`；
- `[sync]` 存在但不是 dict → 报期望表；
- `[sync]` 是 dict 但 `dir` 存在且非 str → 报期望字符串 + 实得类型；
- `dir` 是空串 → 报空值。

诊断只在**文件存在且解析成功**时运行：
`test_missing_config_returns_empty` 要求无文件 → `warnings == []`，
不新增噪音。

近似匹配用 `difflib.get_close_matches("sync", keys)` **默认 cutoff**，
已实测其边界（无需调参即可同时满足"漏报为零"与"既有测试不误报"）：

| 既有/构造段名 | 命中 `sync` | 期望 |
|---|---|---|
| `other`（`test_config_without_sync_section` 用的段名） | **否** | 不误报，该测试天然不受影响 |
| `snyc` / `synv` / `sonc` / `syncx` | 是 | 拼写错误被捕获 |
| `server` / `settings` / `s` / `htc` | 否 | 不制造噪音 |

`sync_dir()` 本体保持不动（返回 `Path | None`，既有测试锁定），
消费侧 `resolve_sync_dir` 不改；文案接线在 `run_push` / `run_pull`
的"未指定同步目录"分支追加 `load_config` 警告行，使错误提示自洽。

### 验收

- 新增测试 ≥4：`[snyc]` 出近似提示 / `dir = 123` 出类型提示 /
  正常配置与无配置**零警告**（防噪音回归，直接断言 `warnings == []`）/
  `[other]` 不误报。
- CLI 面 ≥1：拼错段名时 `push` 的错误输出含该诊断，不再只说"未指定"。

## 4. CFG-3：doctor 文本模式补 sync 段 + 消重复实现（P3）

### 现状复现

`diagnostics._sync_section(root)`（`diagnostics.py:18-32`）
按 `[sync].dir` 自己重了一遍"取路径"的逻辑，与 `config.sync_dir` 是两份代码。
**两份逻辑当前实测等价**（都做 `isinstance(str) and raw` 判空 +
`Path(...).expanduser()`），因此这**不是 bug 而是设计债**：
两份代码只要有一份演化（比如 §3 让 `sync_dir` 接受更多规范化、
或改判空规则），doctor 显示的与 push 实际用的就会静默分叉。
`run_doctor` 文本模式只渲染 memory/source/private_db/catalog 四段，
**完全不读 `sync`**，所以连已有的 `sync.warnings`（语法损坏时才有）
也显示不出来——这在清单 C6 完成项里已作为已知限制记录。

### 方案

- `_sync_section` 改为复用 `config.sync_dir(root)` 取路径，
  `warnings` 仍来自同一次 `config.load_config`（`sync_dir` 不返回警告，
  故本函数保留一次 `load_config` 调用、只把取路径那三行换成 `sync_dir`）；
  保留 `configured` / `dir` / `exists` / `archives` / `bytes` /
  `warnings` 六个字段名与 JSON 结构不变
  （`server.py` 诊断页 `JSON.stringify` 直出，字段不得改名）。
  本项收益是"单一取路径实现"，不改任何可观测输出。
- `run_doctor` 文本输出追加一行同步目录状态：已配置则打印路径，
  未配置打印"未配置"，且 `sync.warnings` 非空时逐行输出。

### 验收

- 新增测试 ≥2：文本 doctor 含同步目录行 / 语法损坏时文本含警告。
- `--json` 输出结构不变（既有 doctor JSON 测试不回归）；
  `_sync_section` 重构前后对同一输入的返回 dict 逐字段相等（等价重构自证）。

是给分层白名单准备的，文档链接不存在"合法的断链"）。

规则：
1. 扫描 `ROOT.rglob("*.md")`，**排除条件用「任一路径段以 `.` 开头」**
   （覆盖 `.git/ .venv/ .pytest_cache/ .superpowers/`），再加 `spike/`
   （用户裁定不动）与 `build/ dist/ node_modules/`。
   取"点开头"而非枚举目录名：实测枚举会漏掉 `.superpowers/sdd/` 这类
   自动生成的台账与 `.venv/` 内第三方 typeshed README——二者今天恰好
   0 断链，但一旦纳入体检，第三方内容与工具自动产物就会被本仓库的
   文档纪律误伤，且 `pip install` 换版本随时可能变红；
2. **先剥行内代码与代码块**：`` `...` `` span 与 ``` ```...``` ``` fence 内的
   内容不参与链接识别——这是 §5 探针 `args` 误报的根因修复，
   也是本脚本第一条测试用例；
3. 链接目标解析：`[text](target)`，忽略 `http(s)://`、`mailto:`、
   纯 `#anchor`；相对目标按**当前 md 文件的父目录**解析；
   目录目标（如 `sessionpack/cli/`）按存在性判定；不存在即违规。

**规则 4：`file://` 与机器绝对路径一律违规**。全仓受检 md 的实测存量只有
`评审意见:3` 一条（`file:///d:/WorkPlace/Pycharm/…`，另一台机器）；
**既往 spec/plans 一律用仓库内相对路径或行内代码引用源文件，
`file://` 在本仓库无惯例存量**，故禁止不会与任何东西冲突。
文案给出路（改写为相对当前 md 的路径）。本 spec 正文已按同一体例
用行内代码引用源文件，自身即可通过脚本，无自我豁免。

| 方案 | 结论 |
|---|---|
| 一律禁止 `file://` / 绝对路径 | **是**：无存量惯例可冲突；仓库文档可移植性本就不该绑定盘符；要修的正是这个形态 |
| 解析后判存在 | **否**（初稿取态）：实测须处理 `file:///e:/x` 去 scheme 得 `/e:/x` 的盘符规范化，首轮未处理 4 条全误判——正确实现可行，但为一个本应禁止的形态维护解析逻辑没有价值 |
