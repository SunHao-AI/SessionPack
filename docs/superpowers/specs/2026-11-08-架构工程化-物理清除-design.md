## 1. 背景（勘察实测）

| # | 事实 | 含义 |
| --- | --- | --- |
| P1 | Spec 12 的删除=隐藏不抹除：墓碑会话的 messages/message_fts 物理行仍在库，历史归档包的 messages.ndjson 仍含全文 | 用户要求"本机彻底清掉某会话内容"时没有出路；本 Spec 补上 |
| P2 | `sessions.status` 无 CHECK 约束（conn.py L49 `NOT NULL DEFAULT 'active'`）；`verify_archive` 不校验 meta 的 status 取值 | 新增 `'purged'` 状态值零 schema 迁移、零格式版本变更 |
| P3 | 复活源头收敛在两处：`upsert_topic`（write.py L62，行不存在则 INSERT active 行）与 `upsert_message`（L85，行不存在则建 active 会话+写消息/FTS）；importer 与 install 全部经这两个入口 | 守卫加在 catalog 层即覆盖 import / install / rebuild 全链路，importer 零改动 |
| P4 | `mark_session_deleted`（write.py L120）的 UPDATE **无 status 条件** | 现状会把 purged 行降级回 deleted，必须加 `AND status != 'purged'` |
| P5 | `archive/build.py` SELECT 无 status 过滤（L69-71），meta.json 写入 status（L93-103） | 重打包天然携带 purged meta；`archive_id` 随内容变化=新包名（ADR-007 规则 4/5：不改旧包、追加产生新包） |
| P6 | `sync.py` push 按精确文件名去重（L63），pull 按包名或 12-hex 尾巴判重（L99-117） | purge 重打包后包名变，同步目录旧包仍可被 pull 拉回——install 端 purged 卡是最后防线 |
| P7 | 读侧 Spec 12 已收口：`list_sessions` / `get_session` / `search_messages` 两分支 / `get_projects` 共四处函数、五处 `!= 'deleted'` 判据（read.py L43/L53/L68/L115/L141） | 判据统一改 `= 'active'` 一处口径收口，purged 行对所有视图隐身且未来加状态不漏 |
| P8 | 退出码只有两个常量：`EXIT_ERROR=1` / `EXIT_USAGE=2`（cli/common.py L16-17）；"会话不存在"现有惯例是 EXIT_USAGE（write_cmds.py L120） | 本 Spec 不新造 `EXIT_NOT_FOUND`；purge 的"会话不存在"沿用 EXIT_USAGE 文案惯例 |

## 2. 目标 / 非目标

**目标**

- G1 本机物理清除入口：`sessionpack delete --session ID --purge --yes`，双旗确认，缺 `--yes` 只打印清单不执行。
- G2 本机库抹除：messages 与 message_fts 行物理删除，sessions 行置 `purged` 终态并清空内容字段；`import` 重扫、`install` 旧包、`rebuild --from-archives` 三条链路都不复活。
- G3 本机归档抹除：受影响归档包重打包（删该会话 ndjson、meta 置 purged），原子替换、自检通过后才删旧包。
- G4 同步目录只读报告：列出仍含该会话的同步副本包名，提示用户自行处置；不代用户写同步目录。
- G5 ADR-007 本机豁免书面化（§8）。

**非目标**

- 跨设备删除传播、批量 purge（`--all-tombstones` 之类）、定时自动 purge、同步目录代删。
- schema 迁移、`format_version` 递增、新退出码常量。
- 撤销通道：purged 是终态，不可 undo。

## 3. 硬约束（沿 Spec 7-12）

`check.py` 五步全绿才可 commit；既有测试不删不改断言；零运行时三方依赖；受管表写 SQL 全部收敛 `catalog/`，`SQL_WRITE_ALLOWED` 豁免集不扩大（install / cli 零写 SQL 字面量）；中文注释/文案/commit。

## 4. 设计

### D1 数据模型：status 状态机，零 schema 变更

```
active ──delete──▶ deleted ──purge──▶ purged（终态，不可逆）
   ◀──undo──┘
```

- 不加表、不加列，`SCHEMA_VERSION` 保持 1；purged 会话**保留 sessions 行**（purge 卡的载体：后续任何导入路径见到 purged 行即跳过），不 `DELETE sessions`。
- purge 落库语义见 D2；purged 行的 `title/summary/content_hash` 清空，行仅剩身份字段+终态。
- 读口径收口（P7）：read.py 五处 `status != 'deleted'` 统一改为 `status = 'active'`；`stats` 维持物理计数不过滤（purged 会话行仍计入 sessions 物理数，其消息已物理删除故消息计数自然减少，doctor/FTS 对账口径不受影响）。
- `get_session_status`（不过滤墓碑，undo 判家用）不改——undo 分支靠它识别 purged 并给出明确报错文案。

### D2 catalog 写侧（catalog/write.py + `__init__` 门面导出）

- **新增 `purge_session(conn, session_id, *, now) -> bool`**（单调用方事务内三语句，函数不 commit，与现有写函数惯例一致）：

  ```sql
  DELETE FROM message_fts WHERE session_id=?;
  DELETE FROM messages   WHERE session_id=?;
  UPDATE sessions SET status='purged', title=NULL, summary=NULL,
         content_hash=NULL, updated_at=? WHERE session_id=? AND status='deleted';
  ```

  UPDATE 带 `status='deleted'` 条件：active 会话与已 purged 会话都打不中，前者由 CLI 前置检查拦截，后者返回 False 由 CLI 报告"已清除"（幂等语义见 §6）。
- **新增 `insert_session_purge_marker(conn, *, session_id, project_id, source_kind, created_at, updated_at) -> None`**：与 `insert_session_tombstone` 同构的 `INSERT OR IGNORE`，status 写 `'purged'`，title/summary 为 NULL。行已存在（任何 status）什么都不做——本机裁决不被包内容覆盖。
- **修改 `mark_session_deleted`**：UPDATE 追加 `AND status != 'purged'`（P4），返回 bool 语义不变。purged 不可被 deleted 降级。
- **修改 `upsert_topic` / `upsert_message`**：函数开头查 `SELECT status FROM sessions WHERE session_id=?`，命中 `'purged'` 即 `return WriteResult(False, False)`。`upsert_message` 的守卫必须在 `INSERT OR IGNORE INTO messages` **之前**，否则消息体与 FTS 行先落盘。守卫在 catalog 层，importer（run.py L137/L140）与 install 自动被覆盖，两调用方零改动。每消息多一次主键查询，导入路径可接受。
- 新符号经 `catalog/__init__.py` 导出但**不进 `__all__`**（对外契约集合冻结惯例，`# noqa: F401`），沿 Spec 12 落地方式。

### D3 安装侧：purged 分支（archive/install.py）

L91-103 墓碑分支之前插入 purged 分支，顺序：purged → deleted → 其余不动。

```python
if meta.get("status") == "purged":
    catalog.insert_session_purge_marker(conn, ...)   # OR IGNORE，行在则不动
    continue   # 跳过该会话 topic/message upsert——包里带全文也不写
```

- `continue` 是防线：重打包后的新包本就无该会话 ndjson，但**他机残留旧包**（含全文）被 pull/install 时在此被挡（P6）。
- deleted 分支逻辑不变；其内部 `mark_session_deleted` 因 D2 的防降级条件不会碰 purged 行。
- 新设备场景：全新库直接装 purged meta 包 → `insert_session_purge_marker` 建卡，后续任何 active 数据不复活（D2 守卫兜底）。

### D4 CLI（cli/parser.py + cli/write_cmds.py run_delete）

```
sessionpack delete --session ID --purge --yes [--data-dir DIR] [--json]
```

- parser：delete 子命令加 `--purge` / `--yes` 两个 store_true 旗标。
- `run_delete` 分支顺序：
  1. `--purge` 与 `--undo` 互斥 → EXIT_USAGE（parser 层或函数开头均可，函数开头检查，parser 保持声明式）；
  2. 前置检查：索引存在（现有惯例）→ 会话存在（不存在 EXIT_USAGE"会话不存在: ID"，沿 P8 惯例）→ `status=='deleted'`（active 时 `--purge` 报"必须先软删除"EXIT_USAGE；purged 时报告"已清除"退出 0）；
  3. 统计消息数、扫描归档目录列出含该会话的包（解包读各 `*/meta.json` 比对 session_id，与现有 search 扫包同量级）；
  4. 打印清单：session_id、消息条数、受影响包文件名；**无 `--yes` → EXIT_USAGE，零修改**；
  5. `purge_session` 事务 + commit；
  6. 逐包重打包（D5）；
  7. 同步目录只读报告（D6）；
  8. 汇总输出（文本与 `--json` 两种，`--json` 字段：`purged/messages_removed/archives_repacked/archives_failed/sync_stale`）。
- undo 分支补充：`get_session_status` 返回 `'purged'` 时报"已物理清除，不可撤销"EXIT_USAGE（现有 `restore_session` WHERE 天然打不中，此改动仅为明确文案）。
- help 短语更新：`软删除会话（墓碑，随归档包传播不复活；--undo 仅撤销本机；--purge --yes 物理清除本机内容，不可逆）`。

### D5 归档重打包（archive/repak.py 新模块）

小模块单函数 `repak_excluding_session(src: Path, session_id: str, dest_dir: Path) -> Path`，纯文件操作零 SQL：

1. `verify_archive(src)` 不过 → 抛错（调用方计入失败清单，旧包不动）。
2. 读原包全部条目，逐条复制到同目录临时文件：该会话的 `messages.ndjson` **跳过**；该会话的 `meta.json` 替换为 purged 精简 meta（`session_id/project_id/source_kind/status='purged'/created_at/updated_at`，无 title/summary）；manifest 同步剔除该 ndjson 条目并重算 `files`、`archive_id`（内容哈希稳定排序合并，复用 build.py 的哈希与命名函数，不复制粘贴算法）；其余条目字节级原样复制（含压缩参数默认）。
3. 临时文件落地为**新包名**（`<project>-<date>-<新archive_id>.zip`），`verify_archive` 自检通过后 `os.replace` 到最终名、再 `os.remove` 旧包；任何一步失败：删临时文件、旧包原样保留、抛错。
4. 返回新包 Path。

**先库后包**：库是权威源、包是派生物，库内 purge（D4 步骤 5）先提交，重打包失败不回滚库——内容已不可能从库复活，失败包仅是残留副本，由报告兜底。多包逐个处理，单包失败不中断其余，汇总"N 成功 / M 失败+原因"，有失败则进程退出码用 `EXIT_ERROR=1`（P8：现有仅两常量，不新造）。

### D6 同步目录只读报告

`sync.py` 只读扫描配置的同步目录（未配置则静默跳过）：按包名（12-hex 尾巴）匹配 purge 前的旧包名与全量解包检查（仅同名嫌疑包），列出仍含该会话的副本文件名，文案提示"请自行删除或重新 push"。**不写不删同步目录任何文件**。

## 5. 归档协议影响与 ADR-007 本机豁免

- `format_version` 保持 1：purged meta 对旧版读取器是"未知 status 的普通会话"，读到的只是空 meta+无 ndjson，无内容泄露（ADR-007 规则 3"忽略不认识的字段/值"）。
- `archive_id` 变化=新包名：是**本机文件改名**，不是跨设备身份变化；旧包名→新包名映射打印给用户。ADR-007 规则 5"不修改旧包"在通用语义下仍成立——重打包产生的新包对旧包是**替换**而非追加，这是对本机副本的显式删除权，不构成对他机持久副本承诺的违反。
- **豁免声明（书面处理，实现时进 ADR-007 指针一节）**：ADR-007 的"归档不可丢"保护的是**用户保有的副本集合**不被程序静默丢弃；`delete --purge --yes` 是用户对**本机副本**的双旗显式行使删除权，语义与"程序丢包"不同。他机/同步目录/离线备份中的旧包不在本机管辖范围：工具只报告（D6），处置权在用户；即使旧包被 pull 回来，install 端 purged 卡（D3）保证内容不复活。

## 6. 错误处理与边界

| 场景 | 行为 |
| --- | --- |
| 索引不存在 | 现有惯例报错（"索引不存在，请先运行 sessionpack import"） |
| 会话不存在 | EXIT_USAGE"会话不存在: ID"（P8 惯例），零修改 |
| active 会话 `--purge` | EXIT_USAGE"必须先软删除"，零修改 |
| 已 purged 再 `--purge` | 幂等：报"已清除"，退出 0，不重复重打包 |
| 缺 `--yes` | 打印清单后 EXIT_USAGE，零修改 |
| `--purge --undo` | EXIT_USAGE |
| purged 会话 `--undo` | EXIT_USAGE"已物理清除，不可撤销"，status 不动 |
| 会话从未归档（归档目录无包） | 跳过重打包，正常成功 |
| 单包 verify 不过 / 读写失败 | 旧包保留、临时文件清理、继续其余包，汇总失败清单，退出码非 0 |
| 该会话是项目唯一会话 | projects 行保留（与 delete 语义一致） |
| 同步目录未配置 | 步骤静默跳过 |
| 重打包后 rebuild --from-archives | purged meta 经 D3 重建 purge 卡，结果与 purge 后状态一致（测试锁定） |
