# ADR-007 归档包采用标准 zip 加 manifest

- 状态：已采纳
- 日期：2026-11-04
- 决策范围：归档包的容器格式与校验方式
- 相关文档：[项目构想](../../项目构想-Trae会话归档与同步.md)、[ADR-006](ADR-006-首发适配器选用明文记忆目录.md)

## 背景

归档包是本工具保留内容的持久副本。索引可以重建，归档对象不能丢，因此格式需要满足三个条件：能被本工具之外的通用工具打开、能在传输后验证完整性、能在格式演进时被旧版本识别并拒绝或降级。

初稿定义了自定义扩展名 `.tarc` 的归档容器，并按内容哈希分片存放对象。这套设计在需要端到端加密、分块传输或去重的阶段是合理的，但首版面对的实际情况是：只有一个适配器、一个用户，归档包通过用户手动复制到另一台设备。在这个阶段引入私有容器格式，需要同步维护格式规范、写入器、读取器、版本兼容规则和第三方实现的参考文档，投入与收益不成比例。

另一个相关约束来自 ADR-001：归档包不能是活动 SQLite 数据库的副本，也不能依赖 SQLite 作为读取入口。这排除了"打包成一个 SQLite 文件"这类看似省事的做法。

## 决策

归档包是一个标准 zip 文件，扩展名 `.zip`，根目录放置 `manifest.json`，其余文件按项目与会话组织。

目录结构：

```text
<project>-<date>-<archive_id>.zip
├── manifest.json
├── sessions/
│   └── <session_id>/
│       ├── messages.ndjson      # 一条消息一行，UTF-8
│       └── meta.json            # 标题、时间、来源定位
└── objects/
    └── <sha256 前两位>/<sha256> # 附件或原文对象，按内容哈希命名
```

`manifest.json` 的最小字段：

```json
{
  "format": "trae-archive",
  "format_version": 1,
  "archive_id": "合并全部文件哈希后取 sha256",
  "created_at": "2026-11-04T12:00:00Z",
  "producer": { "name": "trae-archive", "version": "0.1.0" },
  "adapter": { "id": "trae-cn-memory", "version": 1 },
  "project": { "project_id": "string", "display_name": "string" },
  "counts": { "sessions": 12, "messages": 340 },
  "files": [
    {
      "path": "sessions/<id>/messages.ndjson",
      "sha256": "hex",
      "size": 12345,
      "media_type": "application/x-ndjson"
    }
  ]
}
```

格式规则：

1. `path` 一律使用相对路径与正斜杠，禁止 `..`、绝对路径和盘符，防止解压时越界写入。
2. `manifest.json` 是唯一可信清单。解压时以清单为准逐个校验，zip 内出现未登记文件视为异常。
3. 任何会破坏旧版本读取能力的改动都递增 `format_version`。新增可选字段不递增，读取方必须忽略不认识的字段。
4. `archive_id` 由清单内文件哈希的稳定排序后合并计算，保证同样内容在不同设备生成相同 ID，可用于跨设备去重。
5. 归档包一经生成即视为不可变。会话追加产生新包，不修改旧包。

## 备选的方案

| 方案 | 未采纳原因 |
|---|---|
| 自定义 `.tarc` 容器 | 需要自研规范、读写实现和兼容策略；单适配器阶段没有第三方需要按此格式实现 |
| `tar.gz` | Windows 系统工具支持弱，随机访问单个会话不便，增量读取要整包解压 |
| 散文件目录 | 无法作为单个对象传输，原子性差，用户误改后无法区分"内容变了"和"文件坏了" |
| 单个 SQLite 文件 | 与 ADR-001 冲突；同时把索引与正文耦回一个文件，索引重建不再可行 |
| 直接使用 git 仓库作为归档 | 对非开发者门槛高，二进制对象管理成本高，且把同步策略绑死在一种实现上 |

## 后果

正面影响：

- 用户用系统自带解压工具即可查看内容，不需要安装本工具就能取回数据，这对开源项目的可信度很关键。
- 完整性校验只需 zip 库加 sha256，实现成本和出错面都很小。
- 传输、断点续传、去重都能借用现成能力：对象按内容哈希命名，相同内容不会重复打包。
- 未来接入端到端加密时，可以在这层外面套一个加密信封，内部结构不需要改动。（Spec 14 已按此兑现：docs/superpowers/specs/2026-11-09-同步加密-design.md）

负面影响与接受的代价：

- 归档内容是可读明文。用户若把包放在共享目录，内容会被同机其他程序读到。这一点必须在使用说明里写明，并提供"放入同步目录前先加密"的后续能力。
- zip 的压缩与随机访问性能一般，超大归档（数 GB）解压单个会话需要读取整个中央目录。当前数据规模下不构成问题，规模变化时再评估分卷。
- 依赖 zip 实现的行为差异，例如文件名编码。用 UTF-8 并禁止非 ASCII 之外的约定可以规避大部分问题，但需要在 Windows 与 macOS 上各测一次。
- 清单与内容存在双写窗口：打包过程中断会产生半成品包。通过先写临时文件、校验通过后原子改名解决。

## 实施约束

1. **写入顺序**：先写内容文件并计算哈希，再写 `manifest.json`，最后整体落盘并原子改名；中途失败只留下可清理的临时目录。
2. **校验流程**：`verify` 依次检查 zip 可读、清单可解析、`format_version` 在支持范围、每个文件存在且哈希匹配、清单无重复路径、无未登记文件。
3. **幂等导入**：导入前按 `archive_id` 与单文件哈希查重，已存在的对象跳过，重复导入不产生重复会话。
4. **错误分类**：哈希不匹配、清单缺失、版本过新、路径非法分别给出独立诊断码，便于用户判断是传输损坏还是版本不兼容。
5. **禁用路径**：解压路径必须在目标目录之下，任何越界路径直接拒绝整个包，不做部分解压。

## 验证方式

- 手工修改包内任意一个字节，`verify` 必须报哈希不匹配且不写入索引。
- 删除 `manifest.json`、删除某个内容文件、加入一个未登记文件，三种情况都要被拒绝并给出对应诊断码。
- 在 Windows 与 macOS 上各做一次生成、传输、校验、导入的完整往返。
- 用当前真实数据与 100 倍合成数据各生成一次归档，记录打包耗时与包体积，作为后续分卷策略的判断依据。

## 与其他决策的关系

- 依赖 ADR-001：归档不包含活动数据库文件。
- 依赖 ADR-004：正文对象持久保存，索引可重建，本决策的清单结构服务于这一分离。
- 与 ADR-006 协同：首发适配器的数据规模较小，使 zip 方案的性能代价可以接受；若未来接入大体积源，需要重新评估分卷。
