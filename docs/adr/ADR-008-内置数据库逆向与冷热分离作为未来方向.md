# ADR-008 内置数据库逆向与冷热分离作为未来方向

- 状态：已采纳（作为未来版本方向，当前版本不实现）
- 日期：2026-11-10
- 决策范围：Trae 内置加密数据库的逆向定位、当前方案与未来方向
- 相关文档：[ADR-006](ADR-006-首发适配器选用明文记忆目录.md)、[项目构想](../../项目构想-Trae会话归档与同步.md)、[使用说明-本地只读](../../docs/使用说明-本地只读.md)

## 背景

用户有两个原始诉求：**降低 Trae 数据库体积**、**防止 Trae 因数据过多而崩溃**。由此引出一个更具体的形态：把「冷对话」从 Trae 内置数据库搬到 SessionPack 管理，Trae 里只保留「热对话 + 置顶对话」，实现冷热分离、阻止数据无限增长。

ADR-006 已确认 Trae 私有库为加密容器、处于活动 WAL，自动解析不进入路线图；SessionPack 首发只读明文记忆目录。本 ADR 在该结论上，补充对「直接操作 / 逆向内置数据库」这一方向的调研结论，并把逆向明确定位为**未来版本方向**而非当前实现。

## 调研发现（逆向现状）

以下结论来自公开逆向成果与官方资料，截至 2026-11-10：

| 项 | 结论 |
|---|---|
| 加密 | SQLCipher 4（AES-256-CBC，PBKDF2-HMAC-SHA512，256000 迭代，page_size=4096） |
| 表数量 | 39 张，已逐字段解剖 |
| 核心表 | `chat_session`（会话列表：标题/类型/时间）、`history_v2`（完整对话原文 raw_messages）、`server_history_info`（服务端历史，体量最大）、`chat_turn`（轮次 + token_usage）、`task` / `todo_list` / `session_project` / `agent` / `agent_run` / `mcp_server_agent_relation` / `rules_attachment` 等 |
| 密钥 | **首次启动时随机生成，持久化在进程内存中（hex 字符串）**；获取方式是扫描进程内存（或从本地持久化位置读取） |
| 关键纠偏 | **解密密钥与登录信息无关**：`trae-jwt-token` 是 API 认证令牌，不是数据库加密密钥 |
| 已有开源实现 | [trae-db-decrypt](https://github.com/bigmanBass666/trae-db-decrypt)（Python 3.10+，pycryptodome）、[Oh-My-Trae/trae-db-decrypt](https://github.com/Oh-My-Trae/trae-db-decrypt)（内存扫 key）、[TokenTracker](https://github.com/xiufengsun/TokenTracker)（国际版 shared key） |

三条对方向判断最重要的事实：

1. **读取侧已经可行**：解密 + 读出完整对话 + 按会话归类，已有开源工具铺路。
2. **密钥不是登录信息**：靠「登录信息跨版本解密」不成立；真正拿 key 的路径是「扫进程内存」或「读本地持久化位置」。
3. **写删侧无人敢做且高风险**：见下文「备选方案」。

## 决策

1. **内置数据库逆向 = 未来版本方向，当前版本不实现。** 延续 ADR-006 的红线：本工具不逆向破解加密、不直接写/删/压缩 Trae 数据库。
2. **当前采用**：SessionPack 只做**只读归档明文记忆目录**（`topics.md` + `session_memory_*.jsonl`）；冷对话的完整原文导出与删除**走 Trae 官方 UI**（手动，或未来以 GUI 自动化辅助），不冒写库风险。
3. 若未来做「完整对话备份」，落地形态是**只读解密导出**（见「未来方向技术路线」），而非写删库。

## 备选的方案

| 方案 | 未采纳 / 保留为方向的原因 |
|---|---|
| 直接写删内置数据库实现自动冷热分离 | 需在 Trae 关闭时操作、理解 39 表外键关系、处理 WAL 一致性、每版本 schema 漂移（已历 70 次迁移）；删不干净会导致 Trae 启动崩溃或数据错乱；「置顶/pin」字段在公开 39 表解剖中尚未确认，可能在 VS Code 层而非此库 |
| 靠登录信息解密数据库 | 事实错误：密钥与登录凭据无关，见「调研发现」 |
| GUI 自动化逐条导出+删除 | 可行但脆弱、慢、随 UI 变化失效；仅作为「删除」环节的辅助手段，不作为数据通道 |
| 只读解密导出（未来方向） | **保留**：只读快照，风险低，可拿到完整对话原文，是冷对话归档的正确实现形态 |

## 后果

正面影响：

- 明确划清「当前」与「未来」边界，避免在首版就把逆向/写库这类高风险动作混入。
- 调研结论落档后，未来启动该方向不必从零调研，且关键纠偏（密钥≠登录信息）已记录。
- 当前方案（只读归档记忆目录）风险为零，符合项目「源数据不可变、本地只读」的产品原则。

负面影响与接受的代价：

- 当前方案拿不到完整对话原文（只有摘要与记忆条目），这是 ADR-006 已接受的既有代价，本 ADR 未改变它。
- 冷热分离在当前版本无法自动完成，「保留热 + 置顶、删除冷对话」仍需用户在 Trae 界面手动完成。
- 逆向本身大概率触碰 Trae 的 EULA/ToS，且每版本可能失效——这些成本需在未来启动该方向前正式评估，不在当前承担。

## 未来方向技术路线（当前不实现，仅存档）

若未来启动「完整对话只读备份」，建议形态为独立工具而非并入 SessionPack 主流程：

1. **拿 key**：扫描 Trae 进程内存提取 SQLCipher 密钥（参考 Oh-My-Trae/trae-db-decrypt 的内存扫描方式），或读取本地持久化位置；不依赖登录凭据。
2. **只读打开**：用 SQLCipher 4 以只读方式 ATTACH `database.db`（Trae 关闭或使用快照，避免与活动 WAL 冲突）。
3. **筛冷会话**：按 `chat_session` 的时间 / 类型（`side_chat` / `inline_chat` / `background_chat` / `proactive_chat`）识别冷会话；「置顶」标记需额外逆向确认其存储位置。
4. **导出**：把 `history_v2` 的完整对话（raw_messages）导出为 Markdown/JSON，交由 SessionPack 归档管理（对应「官方导出文件」备用来源，见项目构想 20.2）。
5. **删除**：仍走 Trae 官方 UI，不写删库。

## 与其他决策的关系

- 延续 ADR-006：私有库不解析、不逆向，首发用明文记忆目录。
- 与 ADR-001 一致：不把活动数据库文件作为同步/归档载荷。
- 若未来实现「只读解密导出」，其产物可复用 ADR-007 的 zip + manifest 归档格式，作为新的「官方导出适配器」接入。

## 后续修订指针

- 当 Trae 官方开放「导出/删除会话」的 CLI/API，或明文导出格式稳定后，应优先走官方通道，重新评估本 ADR 的「逆向」方向是否需要保留。
- 若启动逆向方向，需先完成 EULA/ToS 合规评估与「置顶字段定位」两个前置项。
