# ADR-006 首发适配器选用明文记忆目录

- 状态：已采纳
- 日期：2026-11-04
- 决策范围：MVP 1 的数据源与适配器范围
- 相关文档：[项目构想](../../项目构想-Trae会话归档与同步.md)、[ADR-007](ADR-007-归档包采用标准zip加manifest.md)、[字段结构报告](../适配器字段结构报告-trae-cn-memory.md)

## 背景

项目的第一版需要一个可读取、可验证的会话数据源。初稿假设从 Trae CN 的本地数据库导入，并把"能否自动解析"列为可行性验证阶段门。

2026-11-04 在本机完成的只读探测给出了三条事实：

1. `%APPDATA%\Trae CN\ModularData\ai-agent\database.db` 存在，4,496,863,232 字节（约 4.19 GiB），写入时间与当前工作会话同步。
2. 该文件前 16 字节为 `ef 89 24 dd b6 ea ce c3 4a 8e fe 3a 7d b8 0a 47`，不是 SQLite 的 `SQLite format 3` 文件头，判定为加密或私有容器格式；同目录下 `database.db-wal` 为 8.6 MB 且持续写入，另有 `database.db.new-20261015` 等 10 月 15 日的迁移残留文件，以及一份记录了 `project_domain_v2` 迁移水位线的状态文件。
3. 同一用户目录下的 `%USERPROFILE%\.trae-cn\memory` 保存着 95 个明文文件，总计 269.8 KB，分布在 10 个项目目录中，按 `projects/<项目编码>/<日期>/` 组织，包含 `topics.md`、`session_memory_*.jsonl` 与 `user_profile.md`。

第一条否掉了"路径不可知"的不确定性，第二、三条合起来把结论推向另一个方向：加密容器叠加活动 WAL 与版本迁移，意味着任何读取实现都要同时解决格式不可知和格式漂移两个问题；而明文目录已经存在，且结构与工具想要构造的模型高度重合。

同时需要考虑的是，官方导出能力至今没有确认。社区反馈提到部分版本可以逐条导出，也有产品线回复称不支持导出。把首发能力建立在未经确认的菜单上，等于让 MVP 的可用性依赖外部不确定性。

## 决策

MVP 1 只实现一个适配器，数据源为 Trae CN 的明文记忆目录。Trae 私有数据库不实现读取逻辑，`doctor` 与 `scan` 仅报告其路径、大小与格式判定状态。

适配器的读取范围限定为：

| 文件 | 用途 |
|---|---|
| `projects/<项目编码>/<日期>/topics.md` | 按行记录的主题摘要，每行带 `session_id` 与时间前缀，作为会话标题与检索文本的来源 |
| `projects/<项目编码>/<日期>/session_memory_*.jsonl` | 条目化记忆记录，每个会话一个文件，一条记录对应一条消息粒度 |
| `projects/<项目编码>/project_memory.md` | 项目级长期记忆，作为会话补充上下文 |
| `user_profile.md` | 跨项目用户信息，默认不导入，仅用于诊断展示 |

适配器只依赖目录层级、文件后缀和少量稳定字段。模型生成的自由文本按原文保存，不做语义解析、不尝试还原结构化意图，因为那部分内容没有规范，解析规则会随模型版本失效。

## 备选的方案

| 方案 | 未采纳原因 |
|---|---|
| 逆向或解密私有库 | 违反"不逆向、不取密钥"的产品原则；即使技术上可行，格式随版本变化会让实现长期失修 |
| 首发即支持所有产品线 | 各产品线目录结构与导出能力不同，验证成本成倍增加，而价值尚未被验证 |
| 等待官方导出接口 | 接口存在性与时间均不可控，MVP 无法排期，也没有办法先验证检索价值 |
| 只做手动导入（用户自备文件） | 把数据整理成本转嫁给用户，首版体验不成立，也无法自动增量更新 |
| 抓取 IDE 界面（如 UI 自动化） | 脆弱且不可脚本化，对用户正在使用的 IDE 有干扰 |

## 后果

正面影响：

- MVP 可以在不触碰加密组件的前提下跑通完整链路，诊断、导入、检索、导出、归档五项能力都能验证。
- 无需实现数据库快照机制，也无需处理 IDE 运行期间的文件锁，读取路径大幅简化。
- 目录名本身就是项目编码，日期子目录承担时间分区，`Project` 与 `Session` 两级的标识几乎不需要额外推导。
- 数据源体积小（当前 269.8 KB），压测和回归可以快速迭代。

负面影响与接受的代价：

- 数据内容是模型提炼后的摘要与条目，不是完整对话原文。工具能回答"那次关于什么、结论是什么"，不能回答"当时第 7 轮的原话是什么"。
- `session_memory_*.jsonl` 与 `topics.md` 的结构属于未公开的内部格式，没有稳定契约。上游改字段时适配器会失效，且不会有变更日志可查。
- 只有记忆目录参与的会话才能被检索。用户早期未开启记忆能力的历史会话不在其中，覆盖率不完整。
- 项目价值被限定在"检索与续接"，完整归档能力需要等官方导出或其他数据源接入后才能补齐。

## 实施约束

这些约束是为了让上面的代价可控，不是可选建议。

1. **读取白名单**：适配器实现 `declared_paths()`，返回本次操作打算打开的文件集合；核心层在读取前比对实际路径，不一致即中止并报诊断码。同目录下存在 `trae-jwt-token` 和疑似账号标识目录，遍历式扫描不可接受。
2. **最小字段依赖**：只依赖能确认跨版本稳定的字段。无法确认的字段一律降级为原文保存，不做断言。
3. **确定性 ID**：`session_id` 直接取自 `topics.md` 记录前缀与 jsonl 文件名，两者同为 24 位十六进制，可直接作为主键，不必再用路径哈希推导。对其他来源仍需保留内容指纹碰撞检测，保证重复导入幂等。
4. **格式漂移的降级路径**：解析失败时回退为"原文 + 文件元数据"的粗粒度导入，让用户至少能检索到文本，同时报告字段缺失，而不是整批失败。
5. **版本标注**：适配器在兼容矩阵中记录已验证的产品版本与字段覆盖情况；未验证版本一律标为实验性支持。
6. **项目目录归并**：部分项目目录带 `--pN-<hash>` 后缀、部分不带，同一仓库会被拆成两个目录。适配器须去掉后缀后按路径编码归并，否则同一项目将在列表中重复出现，会话也被分散。

## 验证方式

- 抽样读取三类文件，脱敏后记录字段清单，形成字段覆盖表。已完成，结果见[字段结构报告](../适配器字段结构报告-trae-cn-memory.md)。
- 在两个不同近期版本上重复抽样，确认字段集合的差异范围，差异超出预期时收窄依赖字段。
- 用当前 95 个真实文件与约 100 倍合成数据各跑一次全量导入，校验幂等、单条容错与读取边界。
- 在未开启记忆能力的会话上验证覆盖率缺口，并把结果写入使用说明，避免用户误以为能检索到全部历史。

## 与其他决策的关系

- 与 ADR-002（源适配器只读）一致：本决策进一步把只读范围收缩到白名单文件。
- 与 ADR-005（不承诺原生任务恢复）一致：本决策不试图把记忆条目写回 Trae。
- 补齐本决策能力缺口的方向是接入官方导出文件，属于 ADR-006 之后的决策，编号另立。
