## 3. 分项结果

### 3.1 首次导入

- 耗时 50.53 s（含子进程启动，墙钟 50.96 s），吞吐 0.55 MB/s、1137 行/s。
- 读取 57457 行 = 54255 入库 + 3202 去重跳过 + 2 失败（含 1 条重复副本）。
- 峰值 RSS 34.6 MB，约为源数据的 1.24 倍，未出现随记录数增长的内存占用。
- 索引库 91.84 MB，**为源数据的 3.30 倍**。

**发现的实现问题**：本次导入产生 6696 个事务，等于文件数——原型在每个文件末尾强制 flush，平均每个文件只有 8 条记录，批量参数 `--batch 2000` 从未生效。按 50.5 s / 6696 次提交折算，每次提交约 7.5 ms，主要是 fsync 成本。MVP 实现应改为跨文件累积批量提交（按行数或时间触发），否则数据量增长时会近似线性劣化。

### 3.2 幂等

- 对同一数据源强制重扫（`--reparse`，跳过已完成标记），57457 行全部命中已存在记录，新增会话 0、新增行 0，耗时 17.0 s。
- 项目目录归并有效：13 个物理目录归并为 9 个项目，重复副本的 3202 行未产生重复会话或消息。

### 3.3 中断恢复

- 在第 15000 行处强杀进程（退出码 9），已提交 14992 行、完成 1745/1746 个文件，1 个文件停留在批次中间。
- 续跑处理 4951 个文件（跳过已完成 1745，从偏移续传 1），新增 3810 个会话、39263 行，耗时 31.5 s。
- 最终计数与基线逐项相等：sessions 5312、messages 48887、topics 5368、projects 9；`dup_message_ids`、`messages_without_session`、`sessions_without_project` 均为 0。
- 说明：行数据与文件偏移在同一事务内提交，断点不会领先于数据，因此强杀不产生重复行，也不需要事后修复。

### 3.4 容错

- 注入的 1 条截断记录导致 2 次失败（原目录 + 副本目录各一次），其余 48887 条全部入库，`rows_failed` 与失败明细写进报告。
- 失败记录原先只保存文件名，两份目录副本无法区分；本次已改为保存相对路径（见 5 节）。

### 3.5 只读与读取边界

- 导入前后对源目录做全量 sha256 快照：6706 个文件、29,185,519 字节，0 个变更、0 个新增、0 个删除。
- 审计钩子记录的实际打开文件：声明 6696 个，实际打开 6696 个，越界 0 个。
- 声明集合与源目录总文件数的差额为 10 个：9 个 `project_memory.md` 加 1 个 `user_profile.md`，均未被打开。

### 3.6 检索响应

8 个关键词 × 5 次重复，索引已建好、只读连接：

| 方式 | P50 | P95 | 最大 |
|---|---|---|---|
| `LIKE '%kw%'` 全表扫描 | 0.9 ms | 1.9 ms | 4.2 ms |
| FTS5 trigram 短语匹配 | 0.6 ms | 1.6 ms | 4.2 ms |

注意：所有查询都返回 50 条（撞到 `LIMIT 50`），因为合成词表高度重复。**这组数据只证明延迟，不证明检索质量**；构想稿第 10 节已写明检索价值需用真实查询验证，本条不改变该判断。

## 4. 对实现的影响

1. **事务粒度是 D1/D2 的一等约束**：按文件提交在真实数据上同样成立（真实记忆目录 95 个文件、269.8 KB，每个文件同样很小），必须在 MVP 里改为跨文件批量提交，并把 `ImportRun` 的进度上报与批量提交解耦。
2. **索引体积要写进存储诊断**：trigram 索引为源数据的 3.3 倍。诊断页估算应按约 3 倍给出，而不是只报"索引很小"。同时 trigram 是中文子串检索的前提，不能为省空间换成 `unicode61`。
3. **白名单与 ADR-006 存在差距**：原型未纳入 `project_memory.md`（9 个项目各缺一份），MVP 需按 ADR-006 把它加入 `declared_paths()`，缺额会从 10 变成 1。
4. **失败项记录必须含相对路径**，否则双目录副本场景下无法定位。
5. **中断恢复的实现方式可直接沿用**：偏移与数据同事务提交，已验证不丢不重。

## 5. 本次对脚本的修正

开发环境中三个脚本从未执行过，首次运行暴露三处测量缺陷，已修正后重跑（判定标准未改）：

| 问题 | 表现 | 修正 |
|---|---|---|
| Windows 峰值内存恒为 0 | 报告 `peak_rss_mb: 0.0` | 显式声明 `K32GetProcessMemoryInfo` / `GetProcessMemoryInfo` 的 `argtypes` 与句柄类型 |
| 中断测试拿不到已提交进度 | 报告显示"已提交 0 行" | 强杀后直接只读打开目标库统计行数与完成文件数，并断言进度落在中途 |
| 失败项无法区分目录副本 | 两条失败记录同名 | 失败项改用相对 memory 根目录的路径 |

## 6. 未测得与受限项

- **归档打包、校验、重建**：压测当时 D3 未实现，三项指标无对象可测；2026-11-05 MVP 1 实现后已由 `tests/test_archive.py` 与 `tests/test_acceptance.py` 覆盖功能正确性，但尚未在 27.8 MB 合成集上重跑归档性能。

- **32 位系统与大端序**：未测，当前范围只有 Windows 10 x64。
