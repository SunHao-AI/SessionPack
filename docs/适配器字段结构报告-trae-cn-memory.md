# Trae CN 记忆目录字段结构报告

- 日期：2026-11-04
- 数据源：`%USERPROFILE%\.trae-cn\memory`
- 探测方式：只读解析，仅提取文件名、行数、字段名、字段类型与格式匹配率；未记录任何会话正文、项目代码或用户信息原文
- 关联决策：[ADR-006](adr/ADR-006-首发适配器选用明文记忆目录.md)

## 结论摘要

记忆目录的结构比预期更规整，可以支撑适配器实现，但有三处与 ADR-006 的假设不同，需要在实现前修正：

1. `topics.md` 不是 Markdown 文件，而是按行存储的记录文件，每行带 `session_id` 与 `topic_summary_time` 前缀。65 条记录全部符合该格式，解析稳定性好于预期。
2. 两类文件共用同一套 24 位十六进制会话 ID，但覆盖不完整：仅 31 个会话同时出现在 `topics.md` 与 `session_memory_*.jsonl` 中，另有 4 个只见于前者、21 个只见于后者。
3. 同一仓库存在两个项目目录（带与不带 `--p2-<hash>` 后缀），会话被拆分存放，适配器必须做归并，否则同一项目会出现两份记录。

## 目录与文件

| 项目 | 观测值 |
|---|---|
| 项目目录数 | 10 |
| 去除 `--pN-<hash>` 后缀后的不同项目数 | 9 |
| 日期子目录范围 | 2026-07-22 至 2026-11-04 |
| `topics.md` | 25 个，共 65 条记录 |
| `session_memory_*.jsonl` | 60 个，共 252 条记录，单文件 1 至 24 行，均值 4.2 |

| `user_profile.md` | 1 个，10 行 |
| 目录总体积 | 269.8 KB |

目录命名有两种形态：

```text
projects/-d-WorkPlace-Pycharm-FastAPI-Hao/20261104/
projects/-d-WorkPlace-Pycharm-flysee-video-setting--p2-0b7a94085bef1165f415/20261104/
```

前缀是盘符与路径的编码（`-d-` 对应 `D:\`，路径分隔符替换为 `-`），部分目录在路径后附加 `--pN-<16 位哈希>`。`-d-WorkPlace-Pycharm-FastAPI-Hao` 同时存在带与不带后缀的两个目录，说明这套后缀不是随版本统一引入的，而是按项目逐步迁移的结果。

## topics.md 记录格式

每行一条记录，格式为：

```text
[session_id: <24 位十六进制> | topic_summary_time: <YYYY-MM-DD HH:MM:SS>]<主题摘要正文>
```

可用的解析表达式：

```regex
^\[session_id: ([0-9a-f]{24}) \| topic_summary_time: (\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})\](.*)$
```

65 条记录全部匹配，无一条例外，且不含 Markdown 标题、列表符号或空行。正文部分为单行长文本，样本单文件体积 1630 字节、2 行。

同一会话会出现多条记录。35 个不同 `session_id` 对应 65 条记录，即平均每个会话被追加过近两版摘要。导入时应按 `session_id` 聚合，取 `topic_summary_time` 最大的一条作为标题与摘要，历史版本保留为修订记录或直接丢弃，取决于是否需要追溯。

## session_memory_*.jsonl 字段

每行一个 JSON 对象。字段集合稳定为六个，另有一个条件出现的第七字段：

| 字段 | 类型 | 出现率 | 说明 |
|---|---|---|---|
| `message_id` | string | 100% | 消息标识 |
| `message_summary_time` | string | 100% | 摘要生成时间 |
| `intent` | string | 100% | 该条消息的意图归纳 |
| `outcome` | string | 100% | 该条消息的产出或结论 |
| `actions` | array\<string\> | 100% | 动作条目列表，元素均为字符串 |
| `learned` | array\<string\> | 100% | 经验条目列表，元素均为字符串 |
| `compact_summary_meta` | object | 46.7%（28/60 文件） | 压缩摘要的元信息，见下 |

`compact_summary_meta` 的子字段：

| 子字段 | 类型 |
|---|---|
| `created_at_ms` | 整数（毫秒时间戳） |
| `mode` | string |
| `trigger` | string |
| `server_history_id` | string |
| `summary_digest` | string |

## 字段漂移判断

`compact_summary_meta` 的出现不是版本单调演进的结果。按日期目录统计：

| 分组 | 文件数 | 日期目录 |
|---|---|---|
| 含该字段 | 28 | 2026-08-07 至 2026-10-23 |
| 不含该字段 | 32 | 2026-07-22 至 2026-08-06，以及 2026-11-02 至 2026-11-04 |

它在 10 月下旬之后又消失了。结合子字段中同时存在 `mode` 与 `trigger`，可以推断该字段是随摘要生成方式条件出现的运行时标记，而不是某个版本之后固定携带的结构。这个判断对适配器有直接影响：任何把字段当作必选的结构体定义都会在约半数文件上解析失败，全部字段必须按可选处理，缺失即降到默认值或原文保存。

需要说明的是，上述判断基于单机、单用户、三个半月的样本，不能推出"字段集合不会再变"。它能支持的结论只是：在当前版本区间内，六个基础字段稳定，第七字段条件出现。

## 会话 ID 与覆盖缺口

两类文件共用 24 位十六进制 ID，可直接作为关联键：

| 指标 | 数值 |
|---|---|
| `topics.md` 中的会话数 | 35 |
| `session_memory_*.jsonl` 文件名中的会话数 | 52 |
| 两者都有 | 31 |
| 仅 topics | 4 |
| 仅 jsonl | 21 |

60 个 jsonl 文件对应 52 个不同 ID，说明有 8 个会话的记忆文件在项目目录重复存放，与上节的目录分裂现象一致。

覆盖缺口意味着导入不能假设"有摘要就一定有记忆条目"。会话实体需要允许一侧为空：只有 topics 的会话，正文为空，仅有标题与摘要；只有 jsonl 的会话，没有摘要，标题需从 `intent` 或首条记录回退生成。

## 对适配器的影响

1. **Project 归并**：去掉 `--pN-<hash>` 后缀后按路径编码归并目录，把后缀视为同一项目的历史分片。若不归并，同一仓库会显示为两个项目，7 个真实项目会变成 9 至 10 个条目。
2. **Session 聚合**：以 `session_id` 为主键，聚合多行 topics 记录与对应 jsonl 文件；`updated_at` 取两者最大值。
3. **字段可选化**：六个基础字段之外一律视为可选；解析失败的行跳过并计数，不阻断整批导入。
4. **ID 生成**：`session_id` 可直接取自文件内容与文件名，无需再用路径哈希生成。这是对 ADR-006 实施约束第 3 条的修正——确定性 ID 仍需要，但来源从"路径 + 日期"改为"源内 ID"，稳定性更高。
5. **读取范围**：`topics.md` 与 `session_memory_*.jsonl` 之外的 `.md` 文件（`project_memory.md`、`user_profile.md`）默认不进入会话导入，仅在诊断页面展示其存在与体积。

## 跨产品线对比

本机同时安装了 Trae、Trae CN、TRAE SOLO CN 三个产品线，逐一探测结果如下：

| 产品 | 版本 | 数据目录 | 私有库 | 明文记忆目录 |
|---|---|---|---|---|
| Trae | 3.6.4 | `%APPDATA%\Trae` | 869,576,704 字节，头部非 SQLite | `%USERPROFILE%\.trae\memory`，1 个项目目录、1 个 jsonl、0 个 topics |
| Trae CN | 3.4.14 | `%APPDATA%\Trae CN` | 4,500,377,600 字节，头部非 SQLite，WAL 活动 | `%USERPROFILE%\.trae-cn\memory`，10 个项目、60 个 jsonl、25 个 topics |
| TRAE SOLO CN | 未记录 | `%APPDATA%\TRAE SOLO CN` | 2,949,120 字节，头部非 SQLite | 无。`.trae-local` 下仅有 `builtin` |

版本号取自卸载注册表中的 `DisplayVersion`。`resources\app\product.json` 里写的是 `1.107.1`，那是底层壳版本，两个产品线完全相同，不能用来判定兼容性；SOLO CN 没有安装记录，也没有对应安装目录，只在 AppData 下留有 `machineid` 与加密库，推测已卸载或为便携运行，版本无法确认。

三点判断：

1. **路径编码规则是共用的**。两个有记忆目录的产品线使用同一套编码（`-<盘符>-<路径段>`，部分追加 `--pN-<16 位哈希>`），且同一仓库在两个产品线下生成了完全相同的目录名，说明编码由同一组件产生，不是各产品独立实现。
2. **SOLO 没有可读源**。其 `ModularData\ai-agent\work-mode-projects` 下只有两个 24 位十六进制命名的空目录，其中一个含 0.2 KB 的 `TRAE_PROJECT_MOVED_*.md` 标记文件；会话数据全部位于 2.9 MB 的加密库中。SOLO 只能列入诊断范围，不做适配。
3. **记忆目录不是各产品线的必有能力**。Trae 的记忆目录存在但几乎为空（1 个项目、1 个 jsonl、无 topics），Trae CN 才是内容主体。适配器不能假设目录存在即有数据，也不能假设存在 `topics.md`。

Trae（国际版）的 jsonl 已抽样，字段与 Trae CN 同构：同样包含六个基础字段与条件出现的 `compact_summary_meta`，目录编码也完全一致。但本机该产品线只有一个 jsonl、一条记录，1 条样本只能说明结构同源，不足以支撑"两个产品线共用同一适配器"的结论。扩大样本需要在该产品线持续使用后复测，本地无法补足。

## 待验证

- 扩大 Trae（国际版）样本量，确认字段与 Trae CN 的全量一致。
- 在一个明显更旧的版本上抽样，确认六个基础字段是否曾经不同。
- 确认 `--pN-<hash>` 后缀的引入条件，判断后续是否会有更多项目目录被迁移。
- 在开启与未开启记忆能力的会话上对比覆盖率，给出"哪些历史搜不到"的明确说明。

本报告只包含文件名模式、字段名、类型、计数与格式匹配率。所有会话正文、项目路径明细、用户偏好内容均在解析时被丢弃，未写入任何文件，也未离开本机。
